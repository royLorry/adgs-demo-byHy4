# 智能体数据质量技术洞察报告

> **主题**：面向 Agent 产品的数据质量——数据分类法、分类型质量标准与检测方式、技术投资优先级
> **适用体系**：ADGS（智能体数据治理系统）· 与 S2 埋点治理 / S8 质量中心 / S10 Trace 平台 / S11 安全合规协同
> **版本**：v1.0 · 2026-09

## 0. 执行摘要（五条核心判断）

在展开分类之前，先给出本报告最关键的五个判断。如果只读一页，读这一页。

| # | 判断 | 依据 | 对 ADGS 的 implication |
|---|---|---|---|
| **J1** | **智能体数据质量的第一性问题不是"数据错没错"，而是"过程可不可信"**。传统 DQ 检查的是记录值，Agent 场景下真正致命的是"答案对了但计算路径是错的"这类**静默失败** | Trace Integrity 研究显示：正确答案 / 无效 Trace（CAIT）比率高达 **45.8%–59.1%**，即近半数"答对"的用例其执行链路经不起审查 | S8 必须新增**过程态质量**对象（Trace/Span 级规则），不能只稽核表与字段 |
| **J2** | **Agent 自述日志不可作为质量证据**。执行者与记录者是同一个模型时，日志会向"叙事连贯"坍缩 | 实测 **312/400（78%）**的 Agent 执行 Trace 包含对真实执行路径的实质性误报——不是幻觉，是"连贯性伪影" | 质量观测必须在 **API/运行时旁路采集**，与 Agent 自述分源存放并交叉校验（对应"黑匣子 vs 飞行员笔记"原则） |
| **J3** | **Agent 对污染数据零抵抗力，且标准指标完全检测不到** | 1,563 个被污染的工具输出轮次、7 个主流 LLM 的实验中，**没有任何一个 Agent 质疑过工具返回数据的可靠性**；安全违规出现在 **65%–93%**的轮次，而任务完成率、响应连贯性等常规指标**保持稳定** | 必须在**工具返回入上下文之前**设置独立的数据可信度闸门，这是 S8 目前六维模型完全未覆盖的空白 |
| **J4** | **多步链路使质量误差复合放大，单点高准确率在链路上是灾难** | 单步 85% 正确率的 Agent，10 步链路端到端成功率仅 **0.85¹⁰ ≈ 19.7%** | 质量治理重心必须从"终检"前移到**每一步的入参/出参闸门**（Stage-level Gate） |
| **J5** | **自纠正机制无法修复数据质量问题**——这是最反直觉也最重要的一条 | 自纠正依赖"动作失败信号"；而当 Agent 在错误数据上成功完成任务时，**没有失败信号产生，反思不会触发**。数据质量错误在指标上表现为"成功执行" | 不能把质量寄托在 Agent 的自我修正上，必须有外置的、独立的质量观测面 |

**一句话总结**：
> 传统数据质量回答"表里的数据对不对"；智能体数据质量要回答的是——**喂进上下文的每一段内容是否可信、跑过的每一步是否可复现、写下的每一条日志是否保真、产出的每一个声明是否有据可查**。

## 1. 为什么智能体数据质量不是"传统数据质量的延伸"

### 1.1 五个范式断裂

把 DAMA 六维直接套到 Agent 场景会失效，根源在于五个底层假设被打破：

| 断裂点 | 传统数据 | 智能体数据 | 后果 |
|---|---|---|---|
| **① 质量单元** | 一行记录、一个字段 | 一个 chunk、一次 ToolCall、一个 Span、一段上下文 | 无法用 SQL 表达"这个 chunk 切得对不对" |
| **② 状态模型** | 静态快照，可重算 | 有状态的**过程链**（Session → Conversation → Turn → ToolCall） | 错误沿链路**复合传播**，见 1.2 |
| **③ 输入空间** | 有限、可枚举 | 自然语言输入空间**近乎无限** | 无法用覆盖率思维做质量保障 |
| **④ 判定方式** | 规则/阈值可判定 | 大量质量属性**需语义判定**（是否忠实、是否相关、是否安全） | 必须引入 LLM-as-Judge，而 Judge 本身需要被校准 |
| **⑤ 记录者** | 系统与生产者分离 | **执行者与记录者是同一个模型** | 日志可能系统性失真，见 J2 |

### 1.2 一个必须内化的数学事实：复合误差

假设链路上每一步正确率 85%（单看相当不错）：

```
P(10 步全对) = 0.85¹⁰ ≈ 0.197   →   失败率 ≈ 80%
P(20 步全对) = 0.85²⁰ ≈ 0.039   →   失败率 ≈ 96%
```

这与传统 ETL 管道的直觉一致——所以我们在每个 ETL 阶段之间都设了校验。但**当前主流 Agent 架构在步骤之间没有等价的校验层**：上下文窗口跨步骤累积，每一步都基于"含错误的完整历史"推理。

> **洞察**：Agent 的数据管道比 ETL 更需要阶段级校验，而现实是它比 ETL 更少。这是当前 Agent 工程质量最大的结构性欠账。

### 1.3 一个反直觉的机制：为什么质量错误不会被自纠正

行业普遍认为"Agent 能自我反思、重试，所以能自愈"。这个判断只在**执行错误**上成立：

| 错误类型 | 是否有失败信号 | 自纠正是否触发 | 指标表现 |
|---|---|---|---|
| 执行错误（工具报错、超时、解析失败） | ✅ 有（异常/非零退出） | ✅ 触发 | 失败率上升 → **能被发现** |
| 数据质量错误（检索到过期政策、工具返回脏数据、chunk 截断） | ❌ 无（任务"成功"完成） | ❌ **不触发** | 完成率正常 → **完全隐形** |

**这正是 AgentDrift 实验中"安全违规 65–93% 而任务完成率保持稳定"的机制根源。**

> **推论**：质量治理不能内嵌在 Agent 的反思循环里，必须是**外置的第二观测面**——这是 ADGS 作为独立治理层存在的根本理由之一。

## 2. 智能体数据类型全景：一个两轴分类法

### 2.1 分类框架

单一按"结构化 / 非结构化"划分不足以指导质量设计，因为**同一形态的数据在链路的不同位置，质量含义完全不同**（一份 PDF 在入库前是"待解析语料"，进入上下文后是"决策依据"）。因此本报告采用**两轴分类**：

```
                    轴一：结构化程度
       结构化 S        半结构化 SS       非结构化 NS
      ┌──────────────┬──────────────┬──────────────┐
 供给 │ A1 业务主数据  │ B1 知识库结构化│ C1 原始语料    │
 侧L0 │   与行为事件   │   元数据       │  （文档/网页） │
      ├──────────────┼──────────────┼──────────────┤
 过程 │ A2 调用链聚合  │ B2 Trace/Span │ C2 上下文窗口  │
 侧L1 │   指标与成本   │  与工具调用 I/O│  内容与记忆    │
      ├──────────────┼──────────────┼──────────────┤
 产出 │ A3 结构化产出  │ B3 生成的代码  │ C3 自然语言应答│
 侧L2 │  （报表/JSON） │  /SQL/DSL     │  与多模态产物  │
      ├──────────────┼──────────────┼──────────────┤
 反馈 │ A4 评测分与   │ B4 标注与     │ C4 自由文本   │
 侧L3 │   埋点反馈     │   Badcase 结构│   反馈与工单   │
      └──────────────┴──────────────┴──────────────┘
                    轴二：链路位置（供给侧 → 过程侧 → 产出侧 → 反馈侧）
```

**为什么轴二重要**：质量治理的**成本与可行性**主要由轴二决定。供给侧问题可在离线批量修复（成本最低）；过程侧问题只能实时拦截（成本最高但价值最大）；产出侧问题已造成用户影响；反馈侧问题是发现前三类问题的**唯一规模化信号源**。

### 2.2 A 类：结构化数据（4 类）

| 编号 | 类型 | 典型内容 | 特征 | 现有归属 |
|---|---|---|---|---|
| **A1** | 业务主数据与行为事件 | User/Agent/Session/Conversation/Tool 实体；埋点事件 | Schema 固定、量最大、可 SQL | S1 元数据 + S2 埋点 |
| **A2** | 调用链聚合指标 | 工具成功率、P95 延迟、Token 消耗、单次会话成本 | 强时效性、与成本直接挂钩 | S10 Trace 平台 |
| **A3** | 结构化产出 | 报表结果、API 返回的 JSON、抽取的字段 | 有明确下游消费者，错误直接传导业务 | S13 数据服务 |
| **A4** | 评测分与反馈信号 | EvalScore、点赞/点踩、任务完成标记 | 决定优化方向，错误会误导整个迭代 | S10 评测平台 |

### 2.3 B 类：半结构化数据（4 类）

| 编号 | 类型 | 典型内容 | 特征 | 现有归属 |
|---|---|---|---|---|
| **B1** | 知识库结构化元数据 | chunk 的 source/page/section/version/权限标签 | 骨架固定、内容自由；**决定可溯性与过滤能力** | S1 / S13 |
| **B2** | Trace / Span | OTLP 调用链，可嵌套，深度不定 | **Agent 质量的核心证据载体**；体量远大于行为事件 | S10 |
| **B3** | 工具调用 I/O | tool_name + params + result | params 有 Schema，**result 完全自由且不可信** | S10（新增重点） |
| **B4** | 生成的代码 / SQL / DSL | Agent 写出的查询、脚本、配置 | **必须可执行**，是"可执行性"维度的主要对象 | 当前空白 |

### 2.4 C 类：非结构化数据（4 类）

| 编号 | 类型 | 典型内容 | 特征 | 现有归属 |
|---|---|---|---|---|
| **C1** | 原始语料 | PDF/Word/网页/表格/邮件/工单 | 企业 **80%+** 的数据在此；解析质量决定 RAG 天花板 | S13 数据集平台 |
| **C2** | 上下文窗口内容 | 检索到的 chunk、拼装的 prompt、短期记忆 | **直接决定输出质量**，但极少被当作"数据"治理 | 当前空白 |
| **C3** | 自然语言应答与多模态产物 | Agent 回答、生成的图/表/文件/代码 | 面向用户，是质量的**最终呈现** | S10 评测 |
| **C4** | 自由文本反馈 | 用户评论、工单描述、人工标注意见 | 非结构化但信号密度最高 | S10 Badcase |

### 2.5 数据类型 × 体量 × 风险 速查

| 类型 | 相对体量 | 质量风险等级 | 检测成熟度 | 治理优先级 |
|---|:---:|:---:|:---:|:---:|
| A1 主数据与事件 | ★★★★★ | 中 | **高**（现有六维已覆盖） | P2 维持 |
| A2 调用链指标 | ★★★★ | 高 | 中 | **P0** |
| A3 结构化产出 | ★★ | 高 | 中 | P1 |
| A4 评测与反馈 | ★★ | **极高**（错则误导全局） | 低 | **P0** |
| B1 语料元数据 | ★★★ | 中 | 中 | P1 |
| B2 Trace/Span | ★★★★★ | **极高** | **低**（日志保真度未解决） | **P0** |
| B3 工具调用 I/O | ★★★★ | **极高**（零抵抗力） | **极低** | **P0** |
| B4 生成代码/SQL | ★★ | 高 | 低 | **P1** |
| C1 原始语料 | ★★★★★ | 高 | 中 | **P1** |

## 3. 质量维度模型：从"六维"到"6+6 维"

### 3.1 继承的六维（及其在智能体场景的语义迁移）

ADGS 主文档 S8 已定义六维。在 Agent 场景下，其**判定对象发生迁移**，必须重新表述，否则会"有规则但打不中要害"：

| 传统维度 | 原含义 | **智能体场景下的语义迁移** |
|---|---|---|
| 完整性 | 字段不缺失 | 从"字段级"扩展到**链路级**：Span 是否断链？工具调用是否有去无回？检索是否漏召回？ |
| 准确性 | 值反映真实 | 从"值正确"扩展到**语义忠实**：声明是否被证据支撑？（Faithfulness） |
| 一致性 | 口径统一 | 从"跨表一致"扩展到**跨源一致**：Agent 自述日志 vs 旁路采集 vs 下游落库，三者能否对账？ |
| 及时性 | 按时产出 | 从"产出延迟"扩展到**新鲜度**：知识库是否过期？记忆是否 stale？检索到的是不是上一版政策？ |
| 唯一性 | 无重复 | 从"主键去重"扩展到**语义去重**：语料近似重复、评测集样本泄露、chunk 冗余 |
| 有效性 | 符合 Schema | 从"Schema 校验"扩展到**可执行性**：SQL 能否跑通？工具参数能否被接受？ |

### 3.2 新增的六维（智能体特有）

这是本报告的核心提议：**在 S8 现有六维之上新增六个维度**，构成 6+6 模型。

| 新增维度 | 定义 | 为什么必须有 | 典型判定方式 |
|---|---|---|---|
| **① 可执行性 Executability** | 生成的 SQL/代码/工具参数能否被真实系统接受并正确执行 | 答案正确 ≠ 计算正确。CAIT 率 45–59% 说明这是大规模静默失败 | 干跑（Dry-run）/ EXPLAIN / 沙箱执行 / Schema 引用校验 |
| **② 忠实性 Faithfulness** | 每个声明是否有检索证据支撑，有无凭空生成 | 传统"准确性"无法表达"相对于给定上下文是否成立" | 声明抽取 → 逐条 NLI 判定 → 支持率 |
| **③ 上下文适配性 Context Fitness** | chunk 粒度、切分边界、排序是否适合被检索和引用 | chunk 策略直接决定检索上限：**固定切分 71.3% → 文档感知切分 87.6%**（+16.3pp） | 边界完整度、自包含性评分、召回命中分布 |
| **④ 抗污染性 Contamination Resistance** | 工具返回/检索结果进入上下文前是否被校验 | **7 个 LLM、1,563 轮次，零质疑**——Agent 天然信任工具返回 | 多源交叉验证、置信度标记、异常值/注入特征检测 |
| **⑤ 日志保真度 Log Fidelity** | 日志是否如实反映真实执行路径 | **78% 的 Agent Trace 存在实质性误报**，日志本身不可信 | 旁路采集比对、时序自洽校验、Token/耗时与记录一致性 |
| **⑥ 无害性 Harmlessness** | PII、机密、注入指令、违规内容 | 对话内容常含 PII/代码/企业机密（ADGS L4 级）；工具返回可能携带提示注入 | 混合脱敏（正则+NER）、注入特征检测、分级管控 |

## 4. 分类洞察：每一类数据的质量标准与检测方式

> **说明**：每一类给出 ①质量标准（可验收的）②检测方式（可落地的）③关键指标与建议阈值 ④ADGS 落点。

### 4.A 结构化数据

#### A1 · 业务主数据与行为事件

**质量标准**
- 实体身份全局唯一且跨端一致（User / Session / Conversation / Agent 四主体）
- 事件 Schema 注册率 100%，未知事件占比 = 0
- 属性填充率达标（必填 ≥ 99%）
- 跨端（客户端 vs 服务端）同一事件计数差异 ≤ 0.5%

**检测方式**（现有能力已较成熟，重点是**左移**）
- 网关层 Schema 与有效性校验（成本最低）
- 埋点设计阶段规范校验（修复成本次低）
- 数仓层业务准确性校验（修复成本最高，应尽量减少）
- **建议比例**：70% 的规则在前两阶段生效

**关键指标**：未知事件占比 = 0；必填填充率 ≥ 99%；跨端差异 ≤ 0.5%；上报丢失率 ≤ 1%
**ADGS 落点**：S2（埋点治理）+ S8（六维稽核）——**已有能力，无需新增**

---

#### A2 · 调用链聚合指标 ★ P0

**质量标准**
- Span 完整无断链（有 start 必有 end，有 request 必有 response）
- 聚合指标与明细可对账（差异率 ≤ 1%）
- 成本归因准确（Token 计量与账单对账 ≥ 99.5%）
- 实时链路 P95 延迟 ≤ 30s

**检测方式**
- 断链检测：`count(span_start) - count(span_end) ≠ 0` 告警
- 流批对账：实时聚合 vs 离线重算，差异率超阈值告警
- 成本对账：Trace 内 Token 累计 vs 模型厂商账单
- **旁路校验**：抽样比对 Agent 自述的 `latency_ms` / `tokens` 与网关侧实测值（见 A2 与 J2 的关联）

**关键指标**：Span 断链率 = 0；流批差异 ≤ 1%；成本对账 ≥ 99.5%；P95 ≤ 30s
**ADGS 落点**：S10（Trace 平台）+ S8（新增"过程态"规则类型）

---

#### A3 · 结构化产出

**质量标准**
- 产出符合下游 Schema 契约
- 数值在合理值域内，与源端可对账
- **产出可复现**：同样输入重跑结果一致（确定性部分）

**检测方式**
- 契约校验（JSON Schema / 字段级断言）
- 与源端对账（对账一致率 ≥ 99.5%）
- 回归重跑比对（A/B 两个版本产出 diff）

**关键指标**：契约通过率 ≥ 99.9%；对账一致率 ≥ 99.5%
**ADGS 落点**：S13（数据服务）+ S8

---

#### A4 · 评测分与反馈信号 ★ P0

**这是最容易被忽视、但杠杆最大的一类**——评测数据错了，整个优化方向就错了。

**质量标准**
- 评测集可复现：= 筛选规则 + 采样种子 + 标注结果 + 数据快照，四要素齐全
- 评测集无训练集污染（train/test 泄露率 = 0）
- 标注一致性达标（多人标注 Kappa ≥ 0.6）
- **自动评测与人工评测定期对齐**（防止"分数涨了体验没变"）
- 分布代表性：评测集分布 vs 线上真实流量分布，PSI ≤ 0.2

**检测方式**
- 评测集版本化 + 快照（任何分数可追溯到"哪版集、哪些数据、什么标准"）
- 分布漂移监控（PSI / KS 检验），**季度强制刷新**——真实教训：某团队 0.94 忠实度连续 6 个月"优秀"，而客服队列已堆满投诉，原因是 golden set 从 2 月起就不再反映现实
- Judge 一致性监控：自动评分 vs 人工抽评，偏差超阈值即触发 Judge 重新校准
- 泄露检测：评测样本与训练语料的 n-gram / embedding 重叠度

**关键指标**：泄露率 = 0；Kappa ≥ 0.6；分布 PSI ≤ 0.2；Judge-人工一致率 ≥ 85%
**ADGS 落点**：S10（评测平台）——需新增**评测集健康度**模块

---

### 4.B 半结构化数据

#### B1 · 知识库结构化元数据

**质量标准**
- 每个 chunk 可追溯到：源文件 ID + 页码/位置 + 章节路径 + 解析版本 + 权限边界
- 元数据字段完整率 ≥ 99%（无元数据的 chunk 无法过滤、无法溯源、无法按权限隔离）
- 版本与时效标记准确（生效日期 / 废止日期）

**检测方式**
- 入库卡点：chunk 缺失 `source_id` / `page` / `version` 任一字段即拒绝入库
- 权限标签校验：chunk 权限不得宽于源文件权限（**越权泄露高危点**）
- 定期全量扫描：孤儿 chunk（源文件已删除但 chunk 仍在索引）

**关键指标**：元数据完整率 ≥ 99%；可追溯率 = 100%；孤儿 chunk = 0；权限越界 = 0
**ADGS 落点**：S13（数据集）+ S11（权限）

---

#### B2 · Trace / Span ★ P0

**质量标准**
- **日志保真度**：Agent 自述内容与旁路独立采集一致（这是 B2 与其他类型最本质的区别）
- 时序自洽：`parent_span.end ≥ child_span.end`，无负耗时、无未来时间戳
- 嵌套结构合法（子 Span 必须有父 Span，无孤儿节点）
- 关键步骤（工具调用、模型调用）100% 有记录——**不允许"静默跳过"**

**检测方式**
- **① 双源比对（核心手段，对应 J2）**：在 API/网关层旁路采集真实请求/响应/Token/耗时，与 Agent 自述 Trace 做字段级比对，不一致率超阈值即标记"日志不可信"
- **② 时序自洽校验**：负耗时、时钟回拨、父子时间包含关系违反
- **③ 结构完整性**：孤儿 Span、断链、深度超限
- **④ 声明-证据一致性**：Trace 中"成功"状态是否有对应的真实 HTTP 2xx / 工具返回非异常

**关键指标**：双源不一致率 ≤ 1%；断链率 = 0；时序违规 = 0；关键步骤覆盖率 = 100%
**ADGS 落点**：S10 + S8。**"日志保真度"是 ADGS 可作为差异化能力建立的维度**——业界刚意识到这个问题，尚无成熟方案

---

#### B3 · 工具调用 I/O ★ P0（当前最大空白）

**质量标准**
- 入参符合工具 Schema，类型/必填/值域合法
- **出参在进入上下文前必须通过可信度校验**（对应 J3）
- 出参无提示注入特征
- 出参无 PII/机密泄露（尤其外部工具返回）

**检测方式**
- 入参：JSON Schema 强校验 + 干跑（dry-run）
- **出参"Trust but Verify"三板斧**（这是本报告的**首要投资建议**）：
  1. **交叉验证**：关键事实型返回，用第二来源或缓存副本比对，不一致则降级为"低置信"并显式告知 Agent
  2. **置信度标记**：给进入上下文的每段工具返回打 `confidence` 标签，Agent 在关键决策时**必须**参考该标签
  3. **异常特征检测**：返回值量级突变、空结果率突增、schema 漂移、含指令性文本（注入特征）
- 注入检测：出参中检测"忽略之前的指令"类模式 + 异常 Unicode

**关键指标**：入参 Schema 通过率 ≥ 99.9%；出参校验覆盖率 = 100%；注入拦截率；污染数据导致的下游事故数 = 0
**ADGS 落点**：S10 + S8（新增"工具返回可信度"规则族）+ S11（注入与泄露）

> **为什么这是最高优先级**：AgentDrift 实验证明，Agent 对污染数据**零质疑能力**，且常规指标完全检测不到。这是唯一一类"出了问题你永远不知道"的数据。

---

#### B4 · 生成的代码 / SQL / DSL ★ P1

**质量标准（Trace Integrity 七要素）**
生成一个可执行产物时，其 Trace 应当：
1. **显式（Explicit）**：意图与假设被明确记录，而非隐含在 CoT 里
2. **可执行（Executable）**：SQL/代码能被真实引擎接受
3. **Schema 合法（Schema-valid）**：引用的表、字段真实存在
4. **算子忠实（Operator-faithful）**：实际算子与声称的算子一致
5. **可重放（Replayable）**：同样输入 + 同样 Trace → 同样结果
6. **答案一致（Answer-consistent）**：执行结果 == 最终给出的答案
7. **可审计（Auditable）**：第三方可完整复盘

**检测方式**
- `EXPLAIN` / 干跑 / 沙箱执行 → 验证可执行性
- Schema 引用校验：抽取表名/列名与元数据（S1）比对 → 验证 Schema 合法性
- 重放比对：执行 Trace 得到结果 R1，与最终答案 R2 比对 → **CAIT 检测的核心**
- 契约绑定（Execution Contract）：把用户意图 → 表/列 → 算子 → 假设 → 可执行查询 → 结果 → 答案，绑定为一个可检查的工件

**关键指标**：可执行率 ≥ 99%；Schema 引用合法率 = 100%；**CAIT 率（答对但 Trace 无效）≤ 10%**；重放一致率 = 100%
**ADGS 落点**：S10（新增"Trace 完整性"模块）+ S1（提供 Schema 校验能力）+ S8（新增"可执行性"维度）

> **注**：实测中 Contract-First 方案把 CAIT 率从 55%/59.1% 降到 45.8%，说明**契约化有效但远未解决**——这是明确的技术空白与投资机会。

---

### 4.C 非结构化数据

#### C1 · 原始语料 ★ P1

**质量标准**
- **解析保真**：版面还原正确（不乱序、不串栏、表格不丢表头）
- **切分得当**：chunk 边界不切断语义单元，自包含
- **去重**：近似重复率可控（冗余 chunk 会稀释检索精度、抬高成本）
- **脱敏**：PII 已确定性脱敏且脱敏行为可审计
- **时效**：过期/废止版本已标记或下线

**检测方式**
- 解析质量：抽样人工评 + 结构化断言（表格有表头？列数稳定？阅读顺序正确？）
- 切分质量：边界完整度（是否切断句子/表格）、自包含性（脱离上下文能否理解）
- PII：**混合脱敏**（正则处理结构化模式 + NER 处理上下文实体）。实测 F1：纯正则 83.9 / spaCy NER 89.9 / GLiNER 93.9 / LLM 96.0 / **混合 96.7**——混合方案在准确率与吞吐间最优（28 docs/s vs LLM 2.1 docs/s）
- 语义去重：embedding 近邻 + 阈值

**关键指标**：解析成功率按文件类型 ≥ 99%；表格结构完整率 ≥ 98%；chunk 边界切断率 ≤ 2%；PII 脱敏 F1 ≥ 96%；近似重复率 ≤ 5%
**ADGS 落点**：S13（数据集平台）+ S11（脱敏）+ S1（元数据）

> **量化收益参考**：切分策略对检索准确率的影响是**决定性的**——固定切分 71.3% → 递归 78.9% → 语义切分 84.2% → **文档感知切分 87.6%**；加 10–15% overlap 再提升 3–5pp。这是投入产出比最高的单点优化之一。

---

#### C2 · 上下文窗口内容 ★ P0（当前完全空白）

**这是最反直觉的一类：它不在任何数据库里，却直接决定输出质量。**

**质量标准**
- **上下文精确率**：检索到的 chunk 中相关占比达标（减少噪声、节省 Token、降低幻觉素材）
- **上下文召回率**：回答问题所需的 chunk 都被检索到（**最隐蔽的回归**）
- **无污染**：无过期、无矛盾、无注入内容
- **无冗余**：重复/近似 chunk 已折叠（省 Token + 降干扰）

**检测方式**
- 检索侧：`context_precision`、`context_recall`、`Precision@k`、MRR、NDCG
- 生成侧：`faithfulness`、`groundedness`、`answer_relevancy`
- **组合诊断（关键方法论）**——单指标无法定位：

| 指标组合 | 诊断结论 | 处置 |
|---|---|---|
| 忠实度高 + 召回低 | **检索漏召回**，模型在残缺上下文上"诚实地答了一半" | 优化检索/切分，**不要动 Prompt** |
| 召回高 + 忠实低 | 证据齐全但模型仍漂移 | 强化 grounding 约束 / 换模型 |
| 忠实高 + 相关低 | 答得有据但答偏了子问题 | 优化意图识别/查询改写 |
| 精确低 + 成本高 | 噪声 chunk 挤占窗口 | 上 reranker / 收紧 top-k |

- **必须同时监控检索侧与生成侧**：只看生成侧会隐藏检索回归（真实案例：忠实度稳定 0.91 三个月，用户却在投诉 1/6 的回答漏了关键条款，根因是召回只有 0.62）

**关键指标与阈值**：faithfulness ≥ 0.75（≥0.85 为良好）；answer_relevancy ≥ 0.8；context_precision ≥ 0.7；context_recall ≥ 0.8；**引用准确率 ≥ 0.95**（引用错误比不引用破坏性更大）
**ADGS 落点**：S10（新增"上下文质量可观测"）+ S8（新增"上下文适配性"维度）

---

#### C3 · 自然语言应答与多模态产物

**质量标准**
- **忠实性**：每个声明有证据支撑
- **引用正确性三级**：① 有引用 ② 引用段落确实支持该声明 ③ 证据充分（不只是擦边相关）
- **拒答正确性**：语料不足时应当拒答而非硬答；有证据时不该过度拒答
- **校准度**：模型输出的置信度与实际正确率正相关
- 无害：无 PII 泄露、无违规内容

**检测方式**
- 声明级判定：抽取原子声明 → 逐条与证据做 NLI → 支持率 = faithfulness
- 引用三级校验：presence / correctness / sufficiency
- **拒答测试**：评测集中必须包含**不可回答题**，检验是否会"自信硬答"或"过度拒答"
- 无参考答案场景：`SelfCheckGPT`——同源多次采样，只出现一次的声明标记为疑似幻觉（利用"事实可复现、幻觉不可复现"）
- 校准检验：置信分桶 vs 实际正确率，是否单调

**关键指标**：faithfulness ≥ 0.75；引用正确率 ≥ 0.95；拒答准确率 ≥ 90%；PII 泄露 = 0
**ADGS 落点**：S10（评测）+ S11（合规）

> **规模提醒**：faithfulness 0.95 意味着**每 20 句就有 1 句无支撑**。在金融/医疗/法务场景，这个比率不是"质量问题"而是"不可上线"——需要的是**卡点（Gate），不是看板**。

---

#### C4 · 自由文本反馈

**质量标准**
- 反馈可归类（可路由到具体失败模式）
- 无 PII 裸奔（用户常在反馈里粘贴敏感内容）
- 高价值信号（升级工单、负反馈）100% 进入评测集

**检测方式**
- 语义聚类：embedding 聚类 + 主题标注，定位共性 Badcase
- 规则归集：负反馈 / 任务失败 / 异常中断 自动进入 Badcase 池
- 反馈入集：客服升级的 query 天然是最难的样本，应优先入 golden set

**关键指标**：反馈归类覆盖率 ≥ 90%；升级工单入集率 = 100%
**ADGS 落点**：S10（Badcase 归集）

## 5. 值得投入的技术点

### 5.1 技术投资优先级矩阵

按 **业务价值 × 技术成熟度** 定位（成熟度高 = 有可复用方案、可快速落地）：

```
价值 ↑
高   │ ③工具返回校验  ①旁路采集      ②步骤级闸门
     │ ④上下文观测    CAIT/Trace契约  ⑤Judge校准
     │                                ⑥语料解析卡点
中   │ B1元数据可溯                   A4评测集健康度
     │ C4反馈聚类                     B4代码可执行
     │                                ⑨语义去重
低   │                                ⑩多模态产物质量
     │                                ⑪多Agent对比归因
     └──────────────────────────────────────→ 成熟度
        低（需自研）        中          高（有成熟方案）
```

### 5.2 P0 · 立刻投入（0–3 个月）：补齐"完全空白"的四块

这四项共同特征是：**当前 ADGS 能力空白 + 出问题完全不可见**。

#### ① 旁路采集与日志保真度校验 ★ 差异化机会
- **做什么**：在 API / 网关 / SDK 层独立采集真实调用（请求、响应、Token、墙钟耗时），与 Agent 自述 Trace 分源存储并自动比对
- **为什么值得投**：78% 的 Agent 日志存在实质性误报，而**业界尚无成熟产品化方案**。这是 ADGS 建立技术壁垒的机会窗口
- **技术要点**：低侵入探针（OTLP 扩展）、字段级 diff 规则、不一致率基线与告警、"日志可信度"作为一等质量维度输出到 S8
- **衡量指标**：双源不一致率、关键步骤覆盖率、误报发现数

#### ② 工具返回可信度闸门（Trust-but-Verify）★ 唯一"零抵抗力"缺口
- **做什么**：在工具返回进入上下文前，强制经过 交叉验证 / 置信度标记 / 异常检测 三道闸
- **为什么值得投**：7 个 LLM、1,563 轮次实验中 Agent 零质疑；安全违规 65–93% 而常规指标稳定。**这是唯一一类"出了事你永远不知道"的数据**
- **技术要点**：低置信内容显式降级并在 prompt 中标注、关键事实双源比对、注入/异常特征检测、按工具分级（外部工具严格、内部工具放宽）
- **衡量指标**：校验覆盖率 100%、污染导致事故 = 0、误拦截率

#### ③ 步骤级质量闸门（Stage-level Gate）
- **做什么**：把质量校验从"终检"拆到每一步的入参与出参
- **为什么值得投**：复合误差是 Agent 质量的头号数学约束（0.85¹⁰ ≈ 20%）。这是把 85% 的单步准确率"保住"的唯一工程手段
- **技术要点**：轻量同步校验（Schema/值域/非空，< 5ms）+ 重校验异步化；失败时短路而非带病继续
- **衡量指标**：步骤级拦截数、端到端成功率提升幅度

#### ④ 上下文质量可观测（检索侧 + 生成侧双指标上生产）
- **做什么**：把 context_precision / context_recall / faithfulness 作为**生产指标**（不只是离线评测）
- **为什么值得投**：真实案例证明只看生成侧会隐藏检索回归（0.91 稳定 vs 0.62 召回）。而上下文是当前**完全不在治理视野内**的数据
- **技术要点**：线上采样 10–20% 流量做 Judge；检索侧指标可用无标注方法（context relevance）规模化；生成侧需 golden set
- **成本控制**：LLM-as-Judge 单用例 $0.001–0.003，采样 + 分层（快判模型在线、深判模型离线批处理）
- **衡量指标**：四指标达标率、回归发现时效

### 5.3 P1 · 半年内投入（4–9 个月）：把质量"契约化"

#### ⑤ Trace 完整性与 CAIT 指标（Execution Contract）
- 把用户意图 → Schema 元素 → 算子计划 → 假设 → 可执行查询 → 结果 → 答案，绑定为**可检查的工件**
- 重点监控 **CAIT 率**（答案对但 Trace 无效）——这是"静默失败"的量化表征
- 实测 Contract-First 把 CAIT 从 55–59% 降到 45.8%：**有效但远未解决**，自研空间大
- 落地：S10 新增模块 + S1 提供 Schema 校验 + S8 新增"可执行性"维度

#### ⑥ 语料入库质量卡点（解析 / 切分 / 脱敏）
- 卡点下沉到 **element 与 chunk 级**，而非仅文档级
- 文档感知切分（87.6%）+ 10–15% overlap（+3–5pp），相对固定切分（71.3%）是 **+16pp 以上的确定性收益**
- 混合脱敏（正则 + NER）F1 96.7、吞吐 28 docs/s，显著优于纯 LLM（96.0 / 2.1 docs/s）
- **先小后大**：10–20% 的文档驱动 80% 的查询——先做对核心切片，别一上来全量索引

#### ⑦ 评测集健康度与 Judge 校准
- 评测集四要素版本化（规则 + 种子 + 标注 + 快照）
- 分布漂移监控（PSI ≤ 0.2）+ **季度强制刷新**
- Judge-人工一致性定期对齐（≥ 85%），防止"分数涨了体验没变"
- 训练集泄露检测

#### ⑧ 引用质量三级校验
- presence / correctness / sufficiency 三级，而不是"有没有引用"
- 引用错误比不引用更伤（用户更信任带引用的答案）——阈值应设 **≥ 0.95**，低于即为产品风险

### 5.4 P2 · 前瞻布局（9–18 个月）

| 技术点 | 说明 | 时机判断 |
|---|---|---|
| **⑨ 语义级漂移与去重** | embedding 近邻去重、语料时效衰减模型、评测集自动刷新 | 语料规模上万后再投，早投收益有限 |
| **⑩ 多模态产物质量** | 生成图/表/文件的质量判定（目前无成熟自动指标，强依赖人工） | 等指标收敛，先做人工抽检通道 |
| **⑪ 多 Agent 对比归因** | A/B Agent 步骤级耗时与质量对比 | 单 Agent 质量体系跑通后再上 |

### 5.5 反面清单：不建议重投的方向

有判断力地**不做什么**，和做什么同样重要：

| 不投 | 原因 |
|---|---|
| ❌ **指望 Agent 自反思解决数据质量** | 自纠正只对执行错误生效；数据质量错误无失败信号，表现为"成功执行" |
| ❌ **用 BLEU/ROUGE 类指标评估 Agent 输出** | 衡量表层文本相似，与"是否忠实于证据"几乎无关 |
| ❌ **追求全量流量 100% LLM 评测** | 成本与时延不可承受；10–20% 分层采样 + 快/深两级 Judge 是业界收敛做法 |
| ❌ **一开始就全量索引企业知识库** | 200 份精选文档 > 5000 份未治理文档；噪声文档会与正确答案竞争每一次检索 |
| ❌ **把 golden set 当作一次性资产** | 分布会漂移；某团队 0.94 忠实度"优秀"6 个月而客服队列爆满，根因就是 golden set 失效 |
| ❌ **纯靠正则做 PII 脱敏** | 召回仅 72.4%，漏掉近 28% 的 PII（主要是姓名、上下文指代、非标准格式） |

## 7. 风险与开放问题

| # | 风险 / 开放问题 | 说明 | 建议 |
|---|---|---|---|
| R1 | **Judge 本身的质量与成本** | LLM-as-Judge 会漂移、有偏见（偏爱长答案、偏爱自家模型）、单用例 $0.001–0.003 | Judge 版本化 + 定期人工对齐 + 快/深两级 + 采样而非全量 |
| R2 | **旁路采集的侵入性与性能损耗** | 全量旁路在高 QPS 下有成本 | 分层采样：核心链路全量、长尾采样；探针异步化 |
| R3 | **工具校验的误拦截** | 过度校验会打断正常任务，损害体验 | 按工具分级 + 低置信降级而非硬阻断 + 误拦截率纳入监控 |
| R4 | **"日志保真度"缺乏 Ground Truth** | 连旁路采集也可能与真实执行存在观测偏差 | 对账以"可观测事实"（HTTP 状态码、计费 Token、网关耗时）为准，Agent 自述为待验方 |
| R5 | **上下文质量的判定成本高** | context_recall 需要人工标注 must-have chunks | 生产用无标注的 context_relevance 做监控，golden set 用有标注的 recall 做校准 |
| R6 | **多模态产物无成熟自动指标** | 生成图/表的质量难以自动判定 | 现阶段保留人工抽检通道，指标收敛后再自动化 |
| R7 | **合规交叉压力** | GDPR 第 22 条、EU AI Act 高风险系统、HIPAA 均要求可解释与人工复核；Agent 多步链路使"输入到行动"的因果路径难以重建 | 审计链（工具清单、检索上下文、中间输出）必须在 Agent 设计前就规划，事后补代价极高 |
