## 0. 文档信息

本篇是 S2 SDD 的"深化篇"，针对两类用户角色的日均高频场景，做产品形态与可视化的纵深设计：

| 用户 | 日均高频场景 | 当前痛点 |
|---|---|---|
| **产品 / 数据治理** | "我提的埋点方案现在到哪一步？哪个事件在支撑我的需求？相似事件要不要合并？" | 评审流口头化；字典检索粗糙；相似事件排查无工具 |
| **开发 / QA** | "我埋的字段对不对？丢包了吗？自检工具在哪？验收怎么过？" | 自检工具缺失；样本比对靠人工；验收标准不透明 |

**方向 A · 事件字典与方案设计器（信息资产型）**——回答"事件是什么、方案怎么设计、字典怎么治理"。
**方向 B · 实时观测与验收工作台（运营型）**——回答"事件在不在跑、跑得对不对、出了问题怎么办"。

### 2.4 事件分类法

主册 §S2 给的 5 类事件分类（通用 / 交互 / 业务过程 / 系统 / Agent 语义）继续沿用，但每个事件**额外打多标签**：

| 标签维度 | 取值示例 | 用途 |
|---|---|---|
| 主题域 | agent / commerce / growth / infra | 跨主题域检索 |
| 业务对象 | conversation / agent_card / order | 业务对象绑定 |
| 触发主体 | user / system / agent / sdk | 行为来源 |
| 上报端 | web / desktop / mobile / server / agent | 多端查询 |
| 数据敏感度 | public / internal / confidential / restricted | 安全分级 |
| 时效要求 | realtime / near-realtime / batch | 消费时效 |

### 2.5 事件详情页 8-Tab 设计

#### Tab 1 · Schema 定义

- 事件名 + 版本号 + 兼容标记 + 描述
- 属性表格：属性名 / 类型 / 必填 / 枚举 / 值域 / 示例 / 引用公共组 / 备注
- 上报端矩阵：5 端 × (✓ / ✗ / ✗无意义)
- 双端去重规则（如 `primary_side='server'`）

#### Tab 2 · 属性与公共属性组

- 公共属性组继承关系可视化（树状）
- 私有属性 vs 继承属性区分
- 字段类型一致性提示（同名字段在不同事件中类型不一致时高亮）

#### Tab 3 · 版本历史（时间线）

- 每次版本变更的兼容标记、变更摘要、变更人、生效时间
- 支持对比任意两个版本（diff 视图）

#### Tab 4 · 引用本事件的资产

- 反向链接：哪些埋点方案引用了本事件
- 影响面：哪些指标依赖本事件、哪些下游任务消费本事件
- 阻断提示：若修改本事件被这些方案阻塞，会显示冲突

#### Tab 5 · 相似事件

- Top-5 相似事件卡片（含相似度分数：命名 / 语义 / 属性）
- 三个动作：复用 / 合并 / 标记差异

#### Tab 6 · 实时上报样本

- 最近 100 条上报事件瀑布流
- 字段级对比：与 Schema 对比，缺失标红、类型不符标黄
- 导出样本（JSON）

#### Tab 7 · 评论与讨论

- 评论列表（按事件讨论）
- @提及 + 邮件/IM 通知

#### Tab 8 · 监控与告警

- 上报量趋势（折线图）
- 覆盖率（环形图）
- 异常趋势（如 PII 字段意外上报、字段丢失率升高）
- 告警规则配置入口

#### 2.6.2 设计器关键能力

1. **事件搜索与过滤**：按分类、主题域、Owner 筛选
2. **拖拽到画布**：自动展开属性编辑器
3. **属性别名**：事件级可覆盖属性名（场景特化）
4. **公共属性组引用**：方案级自动继承
5. **上报端矩阵**：每个事件 × 5 端的勾选
6. **SDK 代码实时预览**：5 端 Tab 切换，TypeScript / Go / Java / Python / Swift / Kotlin 实时渲染
7. **影响面预检**：设计过程中实时提示"该事件被哪些方案引用、新增属性影响哪些下游"
8. **规范校验**：保存前自动校验，违规项红框标出
9. **保存版本**：每次保存自动生成版本号，可对比任意版本

## 附录 C · 设计决策记录（DDR）

### DDR-01 · 事件字典采用"分类 + 多标签"双层结构

- **决策**：主分类（5 类）+ 多维度标签（主题域 / 业务对象 / 触发主体 / 上报端 / 数据敏感度 / 时效）
- **理由**：单一分类不足以满足检索需求；多标签支持灵活筛选
- **后果**：UI 复杂度略升，但检索能力大幅增强

### DDR-02 · 事件详情页 8-Tab 而非"全部塞一个长页面"

- **决策**：Tab 化（Schema / 属性 / 版本 / 引用 / 相似 / 实时 / 评论 / 监控）
- **理由**：单一页面信息密度过大；Tab 化支持按角色聚焦
- **后果**：Tab 间跳转成本，但信息组织更清晰

### DDR-03 · 方案设计器底部固定 SDK 代码预览区

- **决策**：底部 Tab 实时渲染 5 端 SDK 代码
- **理由**：让开发"看得见"自己将要写的代码，降低认知负担
- **后果**：渲染逻辑需稳定（5 端模板的版本必须严格一致）

### DDR-04 · 实时观测大盘展示"5 端接入状态矩阵"

- **决策**：作为大盘核心组件，矩阵化展示 SDK 版本 / 接入率 / 丢包率 / 上报量
- **理由**：埋点是 5 端工程，端间不一致是大盘最常见痛点
- **后果**：需要 SDK 心跳上报协议（已在 §3.6 定义）

### DDR-05 · 验收工作台按"4 类验收 + 失败详情"组织

- **决策**：不是简单的"通过/不通过"二值，而是 4 类分项 + 每类的失败详情
- **理由**：埋点治理的核心是"哪里出问题"，而不是"是否通过"
- **后果**：UI 信息密度大，但能直接定位修复点

### DDR-06 · 异常事件采用"聚类 + 详情"两层视图

- **决策**：列表展示聚类后的异常（减少告警噪音），详情展示具体样本
- **理由**：单条异常噪声大；聚类后才易看到根因
- **后果**：聚类算法需稳定，避免误聚类
