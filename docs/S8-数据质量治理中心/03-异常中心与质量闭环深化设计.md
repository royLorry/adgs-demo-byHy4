## 1. 深化方向与边界

### 1.1 选型依据

S8 在主册与原需求文档中已经覆盖了"规则 CRUD / 稽核执行 / 异常 / 告警 / 回溯"全部能力。从**用户角色**视角看，这些能力面向三类人：

| 用户角色 | 高频场景 | 当前痛点 |
|---|---|---|
| **数据开发** | "我负责的表哪条规则在卡？阈值合不合理？" | 规则散落在 S8 配置页 + 任务实例配置 + 工单描述三处，找不齐 |
| **数据 Owner** | "这批异常影响了哪些下游？修完要不要回溯？" | 异常列表是平的，看不到影响的指标/报表 |
| **数据治理委员会** | "团队/主题域的总体质量态势如何？" | 只有质量分数字，没有钻取链路 |

主册用算法与接口描述了能力，但**没有给出"打开页面看到什么"**。本篇补的是信息架构、字段布局、交互逻辑——把上述三类用户一天打开 5 次以上的页面写出来。

### 1.2 不在本篇范围的内容

- 不重写主册 §6 关键算法（规则编译、聚合去重、质量分、降噪），只在涉及 UI 层时引用。
- 不重复主册 §10 高可用与 §12 灰度。
- 不重新定义错误码（沿用主册附录 C）。
- 不写后端服务代码（仅写表 DDL 与 TypeScript 接口示意）。

CREATE TABLE dq_rule_recommendation (
    id               BIGINT       PRIMARY KEY AUTO_INCREMENT,
    recommendation_id VARCHAR(36) NOT NULL UNIQUE COMMENT '推荐唯一编号(UUID)',
    rule_id          VARCHAR(36)  NOT NULL COMMENT '被推荐的规则',

### 2.6 规则影响分析算法

#### 2.6.1 输入

```
R: 规则（rule_id, version, 新规则体 or 新阈值)
A: 规则当前绑定的资产列表
L: 规则血缘(dq_rule_lineage)
H: 历史命中数据(dq_result.last_hit_at, fail_count)
SLA: 受影响任务的 SLA 约定
```

#### 2.6.2 计算流程

```
step1 直接资产面 = A
step2 反向资产面 = {a | ∃ r' ∈ L such that r'.relation_type='SUPERSEDES' and r' → a}
step3 同主题域 / 同分层 / 同 Owner 的相邻规则 = ...

step4 预期异常触发量估计:
        expected_fail_per_day = 
            mean(last_30d_fail_count_per_day) × 修正因子(规则阈值变化)

step5 受影响任务数 = SELECT count(distinct task_id) WHERE owner = A ∪ step2 ∪ step3

step6 风险等级:
        HIGH    if 阻塞级(Block) and step4.expected_fail_per_day > 100
        HIGH    if 核心资产在 step1 ∪ step2
        MEDIUM  if 阈值变化幅度 > 5% or step5 > 50
        LOW     其他
```

#### 2.6.3 推荐规则

```typescript
function recommendRulesForAsset(asset: Asset): RuleRecommendation[] {
    const profile = await meta_classify.getAssetProfile(asset);
    
    const candidates = await dq_rule.search({
        industry: profile.industry_tag,
        scenarios: profile.scenario_tags,
        quality_dimensions: profile.dominant_dimensions
    });
    
    const scored = candidates.map(rule => ({
        rule,
        score: 0.4 * industryMatch(rule.tags, profile.industry_tag)
              + 0.3 * schemaMatch(rule.applicable_schema, profile.fields)
              + 0.2 * historicalCoverage(rule.id, profile.fields)
              + 0.1 * recency(rule.last_hit_at)
    }));
    
    return scored
        .filter(s => s.score > 0.6)
        .sort((a, b) => b.score - a.score)
        .slice(0, 5);
}
```

### 3.4 影响面分析

#### 3.4.1 算法（前端调用接口封装）

```typescript
async function getImpactSurface(anomaly: Anomaly): Promise<ImpactNode[]> {
    const rule = await rule_admin.get(anomaly.rule_id);
    const assets = await meta_graph.getDownstream(rule.bound_asset_ids, depth = 5);
    
    // 调用 S7 元数据血缘 SVC
    const downstream = await meta_graph.query({
        direction: 'DOWNSTREAM',
        start_nodes: assets,
        edge_types: ['produces', 'references', 'consumes'],
        max_depth: 5
    });
    
    return downstream.map(node => ({
        id: node.id,
        type: node.type,  // ASSET/REPORT/API/EVENT
        depth: node.depth,
        impact: assessImpact(node, anomaly)
    }));
}
```

## 附录 C · 设计决策记录（DDR）

### DDR-01 · 异常中心采用"聚合键 + 抑制层"两层模型，不做服务端硬合并

- **背景**：主册 §6.2 的去重算法合并了重复异常。
- **决策**：保留所有异常记录在 `dq_anomaly.aggregation_count` 标注聚合条数，前端按"聚合键"分组显示，并叠加"抑制层"（认领/Quiet Hours/同类聚合）。
- **理由**：硬合并会丢失历史细节；聚合键 + 抑制层既保留细节又给用户清晰视图。
- **影响**：DB 量大，但查询走 ES 索引；前端列表与详情不会混淆。

### DDR-02 · 规则详情 7-Tab 而非"全部塞一个长页面"

- **背景**：规则元数据维度多（基础/适用/引用/模拟/被引用/版本/评论），单页面会让信息密度过高。
- **决策**：7 个 Tab 切分，Tab 之间用 URL 锚点保持页面刷新不丢上下文。
- **理由**：Tab 切分匹配用户任务流（编辑规则 vs 看引用 vs 看版本 vs 评审评论）；URL 锚点利于协作时分享链接。
- **影响**：前端需要管理 Tab 状态；移动端待评审，初期不强求移动端体验。

### DDR-03 · 推荐规则采用离线计算 + 在线展示

- **背景**：推荐算法（§2.6.3）涉及资产画像 + 历史命中 + 团队信息。
- **决策**：离线每日 02:00 跑一次，结果存 `dq_rule_recommendation`；前端只展示已计算结果。
- **理由**：实时推荐会强耦合质量门户与推荐引擎，离线任务更可控。
- **影响**：推荐结果有时效性（≤ 24h），过期自动 expires_at 失效。

### DDR-04 · 异常工作台 5-Tab 中"回溯"和"工单"分而不合

- **背景**：回溯是技术动作，工单是组织动作。
- **决策**：两个 Tab 独立，但 Tab 之间通过 back_navigation 互相跳转，URL 用 `#workbench` 共享上下文。
- **理由**：回溯失败经常需要回到工单叫人，分 Tab 能让上下文更清晰。
- **影响**：UI 复杂度略增，但避免"一个 Tab 同时显示 DAG + 工单 timeline"的信息拥挤。

### DDR-05 · 主题域聚焦采用"独立页面 + 同套卡片"，不复用首页逻辑

- **背景**：首页主题域卡片是紧凑的"快照"，详情页需要更深的钻取。
- **决策**：聚焦页独立路径 `/quality/domain/:id`，复用相同的 Sparkline 组件但不直接嵌套首页 DOM。
- **理由**：聚焦页需要"完整 6 维雷达图 + 子主题域树 + 资产表"，首页只需"健康分 + 趋势"。
- **影响**：前后端均需提供两种 API（大盘与聚焦），但口径一致。
